1. Prepare the data

25–30%

Connectors, storage modes, Power Query transformations, and data-quality cleanup. This is the domain your bank tests most (46 usable questions) — mostly Power Query mechanics.

DirectQueryStays in source; queried liveAlways current, no refresh neededHuge datasets, near-real-time needs, source-governed data

Frequently tested trap A model mixing tables with different refresh cadences (e.g. one refreshed daily, another near real-time) needs different storage modes per table — usually a composite model with Dual for shared dimensions. "Minimize load time of visuals" almost always points away from pure DirectQuery.

Common connectors

  • Power Apps data → always Dataverse, not "Power Apps" itself
  • Existing Power BI model with reusable measures → connect to the Power BI dataset/semantic model, not the raw source (minimizes dev effort)
  • Folder of identically-structured files (SharePoint or local) → Get Data → Folder, then Combine & Transform
  • Multiple identical databases to combine → separate queries, then Append

Parameters

  • Used to make a query dynamic (e.g. switch environments, filter values, file paths)
  • Data type must match how it's used (e.g. Text for a folder path)
  • Can be exposed to report users if "Query used as parameter" is enabled

Profile and clean the data

Data profiling tools (Power Query)

  • Column quality — % valid / error / empty
  • Column distribution — distinct & unique value counts
  • Column profile — stats (min/max/avg/std dev) for the whole column
  • Enable via View tab; default only profiles the first 1,000 rows unless you switch to "profile entire dataset"

Fixing import errors

  • Errors from bad data type conversion → fix the source column type, don't just Replace Errors as a band-aid
  • Replace Errors lets you swap error values with a constant (e.g. 0)
  • Remove Errors drops the whole row — use only when those rows are truly junk

Transform and load the data

OperationWhen to use
Merge queriesCombine two tables side-by-side by matching key column(s) — adds columns. Choose join kind: Left Outer (keep all of left), Inner (only matches), Full Outer, etc.
Append queriesStack tables with the same columns on top of each other — adds rows
Group byAggregate rows into summarized groups
PivotTurn row values into columns
UnpivotTurn columns into rows (e.g. Jan/Feb/Mar columns → one "Month" column) — classic exam scenario
TransposeSwap rows and columns entirely
Reference queryNew query that points to another query's output without duplicating its steps — changes upstream propagate
Duplicate queryIndependent copy — upstream changes do not propagate
Recurring pattern "One row per customer with unpivoted city/region/country" or "combine Table1 + Table2 into one deduplicated column" → sequence is almost always import both → Append → Remove Duplicates (or Merge, if you need columns from a related table rather than combined rows).
Fuzzy matching Use Fuzzy Matching in a Merge when join keys are user-entered / unsanitized (typos, casing, extra spaces) — e.g. matching a web-form "Customer Name" against a clean master list.

2. Model the data

25–30%

Relationships, star schema design, and DAX. Fewer raw questions in your bank (32) but each tends to require deeper reasoning — this is where exam time gets eaten.

Design and implement a data model

Star schema

  • One central fact table (transactions/events) + surrounding dimension tables (descriptive attributes)
  • Preferred over a single flat table or snowflake schema for performance and DAX simplicity
  • Relationships flow fact ← dimension, filtering from the "one" side to the "many" side

Cardinality & cross-filter direction

  • One-to-many is the default and safest choice for fact-to-dimension links
  • Single cross-filter direction is the default; Both (bidirectional) can cause ambiguity and circular filtering in complex models — use sparingly
  • Many-to-many needs a bridge table in most well-designed models

Role-playing dimensions

  • One dimension used multiple ways (e.g. one Date table for both OrderDate and ShipDate)
  • Handled with USERELATIONSHIP() in DAX, or by importing the dimension multiple times with distinct names

Date table

  • Should be a proper contiguous calendar table, marked as a Date Table in modeling settings
  • Required for time-intelligence DAX functions to behave correctly
  • Can be built with CALENDAR() / CALENDARAUTO() as a calculated table

Create model calculations by using DAX

CALCULATE()

Changes the filter context of an expression — the core of most DAX measures

SAMEPERIODLASTYEAR()

Time intelligence: shifts the current filter context back one year

TOTALYTD / QTD / MTD

Running year/quarter/month-to-date totals

DATEADD()

Shifts dates by any interval (day/month/quarter/year)

USERELATIONSHIP()

Activates an inactive relationship for one calculation (role-playing dimensions)

SUMX / AVERAGEX

Iterators — evaluate an expression row-by-row, then aggregate

ALL() / ALLEXCEPT()

Remove filters (fully, or all-but-specified columns) — common in % of total measures

RANKX()

Ranks values within a given context

Calculated column vs. measure vs. calculated table

  • Calculated column — computed per row, stored in the model (uses RAM), usable as a slicer/axis field
  • Measure — computed on the fly per query context, not stored, aggregation-aware
  • Calculated table — new table generated entirely by a DAX expression (e.g. a Date table)

Semi-additive measures

  • For values that shouldn't simply sum across time — e.g. account balances, headcount
  • Typically wrapped with LASTDATE / FIRSTDATE / CLOSINGBALANCE

Calculation groups

  • Reusable sets of DAX logic (e.g. Time Intelligence: YTD/PY/QTD as one group) applied across many measures
  • Avoids duplicating the same time-intelligence logic per measure

Optimize model performance

Quick wins Remove unused columns/rows before anything else. Prefer numeric/integer keys over text for relationships. Reduce granularity when visual-level detail doesn't need row-level data. Use Performance Analyzer to isolate whether a slow visual is the DAX, the visual rendering, or the query itself; use DAX query view to test/profile measures directly.

3. Visualize and analyze the data

25–30%

Report building, interactivity, storytelling features, and the built-in analytics tools. Your bank's largest usable pool (41 questions) — heavy on named features, so know what each one is called precisely.

Create reports

Choosing a visual

  • Trend over time → line/area chart
  • Comparison across categories → bar/column chart
  • Part-to-whole → pie/donut/treemap (use sparingly, few categories)
  • Relationship between two measures → scatter chart
  • Single KPI vs. target → card, KPI visual, gauge

Copilot in reports

  • Can generate a narrative visual summarizing a page in text
  • Can suggest an entire new report page or content for one
  • Can summarize the underlying semantic model

Enhance reports for usability and storytelling

FeatureWhat it does
BookmarkCaptures the current state of a page (filters, visibility, slicer values) to jump back to — powers custom navigation and "story mode"
Custom tooltip pageA separate report page shown as a tooltip; must be built small, and marked "Allow use as a tooltip" in Page Information on the tooltip page itself, then set as the tooltip on the target visual
DrillthroughRight-click a data point to jump to a filtered detail page; configured via the Drillthrough well on the target page
Sync slicersApply one slicer's selection across multiple pages via the Sync slicers pane
Selection paneGroup, layer, hide/show individual visual objects on a page
Personalize visualsLets report consumers (not just designers) swap visual types/fields at view time — must be enabled by the designer
Frequently tested trap For a custom tooltip: the "Allow use as tooltip" toggle is set on the tooltip page, not the target page. Getting the two pages backwards is the most common wrong answer pattern in this topic.

Identify patterns and trends

The "Analyze" feature

  • Right-click a data point → Analyze → "Explain the increase/decrease" for quick AI-driven explanations

AI visuals

  • Key influencers — what drives a metric up or down
  • Decomposition tree — drill into what's contributing to a value across dimensions, AI-suggested splits available
  • Q&A visual — natural-language querying of the model
  • Smart narrative — auto-generated text summary

Other analytics

  • Grouping / binning / clustering for numeric or categorical simplification
  • Forecasting, reference lines, and error bars — added via the Analytics pane on line/scatter charts

4. Manage and secure Power BI

15–20%

Smallest official weight, but don't skip it — RLS and gateways alone show up in ~35 of your practice questions, more than almost any other single topic.

Create and manage workspaces and assets

Workspace roleCan do
AdminEverything, including managing workspace access/roles and deleting the workspace
MemberPublish, edit, and share content; manage most content settings (not workspace-level access)
ContributorEdit and publish content, but can't share it with others
ViewerRead-only access to content

Gateways

  • Required whenever a scheduled refresh needs to reach an on-premises data source
  • Not required for purely cloud sources (Azure SQL, SharePoint Online, etc.)
  • Setup order: install gateway → add data source to it → map the semantic model to that data source → assign dataset owner/credentials

Refresh types

  • Scheduled refresh — full reload on a timer (up to 8x/day on Pro)
  • Incremental refresh — only reloads recent partitions; needed for very large fact tables to stay within refresh time limits

Distribution

  • App — packaged, curated way to distribute a workspace's content broadly
  • Subscriptions — scheduled email snapshots of a report/dashboard to yourself or others
  • Data alerts — notify when a card/KPI crosses a threshold (dashboards only)

Secure and govern Power BI items

Frequently tested — Row-Level Security RLS sequence: (1) define role(s) and DAX filter expressions in Power BI Desktop → (2) publish the report → (3) in the Service, open Security for the semantic model → (4) assign members/security groups to each role. Static RLS hardcodes a value per role; dynamic RLS uses USERNAME()/USERPRINCIPALNAME() against a table so one role definition works for many users.

Access levels

  • Workspace role — access to everything in the workspace
  • Item-level access — share a single report/dashboard without full workspace access
  • Semantic model access ("Build" permission) — lets someone build new reports on top of your model without opening it directly

Sensitivity labels

  • Classify and protect content (e.g. Confidential, Public); can restrict export and encrypt on download
  • Can inherit from the source data or be applied manually in the Service/Desktop
